# Architecture

Studio has three boundaries: acquisition writes fixture files and the fixture manifest `downloads.csv`; concrete Python workflows execute APB subprocesses and write reports; the TypeScript viewer reads those reports.

## Modules

| Component | Responsibility |
| --- | --- |
| `proteobench_fixtures.py`, `fixture_store.py` | `fixture` CLI, downloads, the fixture manifest `downloads.csv` |
| `zenodo_fixtures.py`, `fetch.py` | Zenodo records from `config/zenodo.toml`; resumable, verified downloads shared by every source |
| `table_storage.py` | Plain or gzipped vendor-table storage, chosen once per download |
| `corpus/config.py`, `corpus/selection.py` | Corpus files by name; corpus keys resolved through the manifest |
| `corpus/tables.py` | Exact CSV schema and explicit joins |
| `corpus/models.py` | Versioned JSON records |
| `corpus/runner.py` | Linear subprocess execution, telemetry, logs, progress and final reports |
| `workflows/workflow_<name>.py` | Workflow-owned ordered APB commands; see [Adding a workflow](workflows.md) |
| `workflows/artifacts.py`, `workflows/software.py` | Declarations shared by every concrete workflow |
| `corpus/discovery.py` | Packaged workflows and the tools, parameter inputs and resource table each declares |
| `corpus/workflow_cli.py` | The CLI contract and `WorkflowContext` every workflow script shares |
| `corpus/parameters.py` | Required, optional or ignored vendor-parameter dependencies |
| `corpus/runs.py`, `corpus/cli.py` | Snapshot preparation and Snakemake invocation |
| `workflow/Snakefile` | One dataset rule and one index rule |
| `corpus/clean.py` | Delete saved runs or clear previous results before forced reruns |
| `corpus/catalog.py` | Run catalog `index.json`: visible runs and their observed output extensions |
| `corpus/viewer_inputs.py` | `input_kinds.json` and `proteobench_references.json`, recorded when a run starts |
| `corpus/oddities.py` | `oddities.json` from the producers' recorded summary entries |
| `corpus/search_settings.py` | `search_settings.json` from apb2's recorded search parameters |
| `corpus/publish.py` | `corpus publish`: the viewer and every saved run copied for a plain file server |
| `viewer/src/corpus/`, `viewer/src/fixture/` | Typed browser state, projections and rendering |
| `viewer/src/shared/` | Shared dependency adapters |
| `corpus_viewer/web/`, `fixture_viewer/web/` | Generated Vite bundles packaged with Python |

The workflow scripts depend on the shared corpus runner. The corpus runner never imports APB domain packages or analyzes scientific matrices. Its index job collects the producers' recorded summary entries from representation JSON into `oddities.json`, with explicit source, per-dataset entries and affected-dataset counts by software and producer metric. The projection selects the displayed successful scientific output, including FASTA-verified intermediates when a later step fails. The same job reads apb2's recorded search parameters from that representation into `search_settings.json`, counting per software the datasets that recovered each setting. The server serves static files and performs no workflow actions. The stage registry and pipeline YAMLs have been removed.

## Inputs and snapshots

Corpus files in `corpuses/` are hand-curated lists of dataset keys with exactly `dataset,note`. A run resolves each key through the fixture manifest under an independently configured data root into one resolved row, `dataset,input_file,vendor_parameter_file,module,software_name`, whose paths are the stored files, plain or gzipped. A workflow receives the selected file path and the resolved CSV, locates its row, and performs any join itself. `workflow_proteobench.csv` uses `module` and supplies `fasta`, quantification `level` and the module's `sdrf`; `module` itself names apb-proteobench's packaged module; the pMultiQC workflow requires `peptidoform_ion` and therefore emits H5AD for HDF5 storage. `workflow_aggregate.csv` uses `software_name` and supplies `method`, a `;`-separated list of apb-aggregate selections run as chained steps over all quantitative layers. A workflow reads `workflow_<name>.csv` unless it declares `WORKFLOW_TABLE` to share a sibling's table, as `proteobench_run` and `proteobench_pmultiqc` share `proteobench`'s.

The Fixture Manager downloads and manages; corpora decide what to run. `fixture download all` acquires every ProteoBench module, including plasma and entrapment, and every Zenodo record in `config/zenodo.toml`; `fixture download NAME` acquires exactly the keys `corpuses/NAME.csv` lists, and refuses keys no catalogued submission or configured dataset provides. Either refreshes the catalog and FASTAs and rebuilds `downloads.csv` from disk, one row per catalogued submission and configured Zenodo dataset with its `dataset_dir`, stored input and parameter paths, size and status; it never writes a corpus file. Zenodo datasets land in `zenodo/<record>/<dataset>/`; one may name its folder as input, which APB reads as related tables, and may have no parameter file, which full-level conversion and aggregation workflows accept using result-producer software hints (see [External datasets](datasets.md)). The `proteobench_plasma` workflow runs the `proteobench_pmultiqc` steps with `--layer X`; apb-proteobench's `dia_plasma` module turns that into each software's un-normalized layer through apb-catalog, because upstream scores plasma on un-normalized DIA-NN quantities. The checked-in extended routine has 14 bounded examples. The independent routine_pb inventory selects its 12 catalogued ProteoBench quantification inputs for the single-call `proteobench_run` scoring workflow, excluding the Zenodo MaxQuant entrapment folder. Its selected aggregation is primary-X median polish; general all-layer aggregation is deferred. MaxQuant entrapment has no standalone corpus; its multifile folder is a routine dataset. A corpus name is its file stem, and `all` is reserved for every downloaded dataset. A selected dataset the manifest knows but has not stored runs no tool: run preparation records it in `run.json`, and the Snakemake dataset rule writes its `not_downloaded` report, so a forced clean cannot lose it; `--strict` refuses such a run, and an unknown key always fails. `ExecutionSettings` explicitly names the corpus name, the corpus file (null for `all`), optional workflow table, the fixture manifest, data root, workflow, format, a `tools` map holding one resolved path per executable the workflow declared, cores, and any selection. Run launch publishes the resolved settings and CSV snapshots inside the stable combination directory; the read-only `configure` command reports the main settings file, corpus files, effective roots, and immediate defaults.

Ordinary runs enable force by default: before execution the selected combination’s previous generated artifacts, reports, logs, indexes and legacy history are deleted, without archiving or touching fixtures. Dry-runs never delete results. At launch, the full source inventory, selected rows, one-row dataset CSVs, selected input-size metadata, optional workflow table, settings, and workflow source are copied into `<output_root>/corpus/<corpus>/<workflow>/<format>/`; content-identical snapshots keep their mtimes. Input size is joined explicitly from the resolved `input_file` to `downloads.input_file_path`. Each dataset rule declares its own CSV, input and parameter files, workflow/runtime sources, workflow table, tool launcher, distribution metadata, and editable tool sources. Its command, row, and observed tool versions are Snakemake parameters. `run.json` links the current snapshots and expected reports before execution. The viewer selects the one live stable combination directly; schema-1 hashed directories remain on disk but stay hidden.

## Reporting and progress

Each APB step records its name, argv, inputs, outputs, timestamps, runtime in seconds, peak process-tree RSS in bytes, exit code, separate stdout/stderr, warnings and errors. Present inputs and successfully generated file or directory artifacts also record their byte sizes. The runner writes atomic progress snapshots during execution and a final report after all attempted steps settle. Subsequent steps become skipped after an APB failure.

An APB failure produces a failed report and a successful workflow-process exit. An inability to run the reporting framework fails the Snakemake rule. The index is published only after all final reports validate. Scheduler completion and APB success remain separate visible fields.

The viewer uses only JSON/CSV/text URLs. It shares the Fixture Viewer frontend architecture: a Lit light-DOM shell, pure projections, focused panel controllers, renderer adapters, and the same locked npm dependencies for Tabulator, Plotly, and D3-DSV; `app.ts` is only the composition root. A shared strict TypeScript/Vite project builds both entries, bundles dependencies locally, and publishes content-hashed scripts and styles into each Python web root. Node is a development dependency; the installed viewer needs no Node process or CDN. CI verifies types, browser behavior contracts, and bundle freshness. Its identity endpoint hashes the canonical store and web roots, allowing `corpus view` and `corpus view stop` to distinguish the requested viewer from another store or service on the same port; stopping also requires the recorded PID to own the exact localhost listening socket before signaling. File responses stream from disk. Generated-artifact links stay inside the corpus store under `/data/`; input, parameter and FASTA links open the fixture store under `/fixtures/`, which a published site serves beside the runs. The catalog file `index.json`, rewritten when a run starts, is marked running, finishes or is cleaned, exposes the absolute store root so the Run manifest panel can show the artifact directory. Its output-extension map reads each dataset’s latest observed scientific output from successful steps, caches report summaries by path, mtime and size, and invalidates them when reports change or disappear. Runs displays those actual extensions in its Output column, and Run overview summarizes the complete run’s observed scientific extensions independently of dataset filters. Missing observations display an em dash; mixed outputs retain every observed extension. Format remains the backend selector, so HDF5 does not substitute for `.h5ad` or `.h5mu`. The viewer polls at two-second intervals and reads progress until a final report becomes available. Run selection requests an immediate refresh, serialized with polling so loads cannot overlap. A new operation invalidates cached reports. It displays interrupted work when the operation ended before a dataset produced a final result. The dataset table exposes only the last observed scientific output of a succeeded step. Show more retains all declared paths, distinguishes missing outputs from existing failed-step artifacts through independently observed sizes, and selects the representation sidecar belonging to that displayed output, falling back to the last readable representation. Three main tabs separate Runs, Run overview and File details. Runs displays a catalog header without selected-run identity, progress or a run switcher; returning to the catalog retains the opened combination. Run overview and File details display a persistent selected-run banner naming corpus, workflow, format, observed output extensions and dataset progress independently of run filters. Change run reveals the compact native selector; the Runs sidebar owns run search. After option changes, the shell synchronizes the native selector with the selected run. Runs places corpus, workflow and format facets beside the sortable catalog; the selector uses the same filters and pins the active combination when excluded. Run overview places dataset search and multi-select software, module, result and oddities dropdowns beside Datasets, Visualizations, Oddities, Search settings, Settings & inputs and Scheduler log subtabs. Pure typed filters combine search tokens with AND, selected values within a facet with OR, and facets with AND; each facet count applies all other filters. The composition root passes filtered rows to the dataset table and charts, while retaining complete rows for report summaries and scientific selection. Settings and logs remain full-run evidence. Snapshot links live inside their owning settings subtabs; optional links clear when selecting another run. Dataset filters persist across polls and reset when selecting another run. Share view builds a link from the current run, tabs and opened dataset with the pure `view-link.ts` projection; the composition root reads such a fragment once, clears it, and applies it after the named run loads. File details places dataset search above its left dataset chooser and keeps the remaining dropdowns in a collapsed Filter options control; an opened file and scientific subtab survive being filtered out. Chooser entries show software, actual file or folder kind with an icon, and persisted input size. Software repeated in the full run also shows its module, even when filters leave only one entry; full paths stay in hover details and Inputs & outputs. The run records each selected input's kind in `input_kinds.json` when it starts, resolving inputs beneath its data root with the usual path and symlink guards. The browser loads those kinds once per run selection and reads sizes from persisted acquisition metadata. Show more opens that view directly on AnnData, with its objects in nested subtabs and Structure alongside it. Inputs and outputs, APB-owned metadata, and the complete representation JSON remain available as detail subtabs. The Inputs & outputs renderer uses a pure workflow projection to match each input’s exact path to the most recent preceding output, retaining report order, step status and later consumers without mutating reports. Step cards separate inputs and outputs; per-file handoff labels identify producers and consumers, while full paths, exact sizes and supporting files stay expandable. Missing output observations retain their declared path without a download link. Vendor source links must match the selected row’s recorded source path; generated inputs use the same guarded store URL as their producing output. The metadata projection preserves the root part and each level part and renders each at its physical path, `uns["apb"]` or, in H5AD, `uns[level]["apb"]`; it does not move missing shared provenance out of a modality. Each AnnData panel contains nested axes, one-tab-per-layer, and aligned-structure scientific views only. Both tab levels render lazily so Plotly measures a visible container. Known embedded provenance JSON is decoded defensively for older sidecars. It renders categorical counts and Plotly summaries only for quantitative layers without computing proteomics statistics. The execution report remains a secondary diagnostic in the files tab. Its corpus visualization projection creates a workflow summary followed by dynamic tabs for each recorded step/tool pair. Every tab plots runtime, peak RSS and non-representation artifact size against vendor input size. Workflow runtime is the sum of observed step runtimes, workflow memory is their maximum peak RSS, and its artifact series remain separated by step and software; partial failed-workflow evidence remains visible and absent measurements remain absent.

The Score comparison panel is enabled by the run's declared `apb-proteobench` tool, independent of workflow names. Its pure projection reads score observations from successful version-7 AnnData representation outputs and pairs exact input, score name and completeness cutoff with downloaded submission results. When the run starts it records, in `proteobench_references.json`, each selected submission's metadata resolved through the fixture store by repository and hash, after checking the submission identity and data-root and symlink confinement. Downloaded non-standard NaN/Infinity values become JSON null; finite score values are unchanged. The one reference read starts only when the tab opens, and plots render when their facets enter view. The panel applies dataset filters, keeps stable software colors, shows paired counts and unmatched evidence, and plots one facet per metric with equal X/Y numeric limits and an identity line. A checkbox switches the renderer to difference versus arithmetic mean, with a zero reference line and symmetric difference limits; the same paired observations and filters drive both views, with no additional reads. Entrapment selects an APB confidence kind explicitly and compares scalar summary scores; FDP curves are not pooled into that comparison. The browser only matches observations and subtracts them for displayed differences; neither viewer nor server computes ProteoBench scores.

## Verification

Unit tests exercise CSV validation, explicit join failures, workflow step construction, subprocess logs, unavailable commands, missing files, skipped steps and failed report publication. Integration checks run the named vendor fixtures through the actual APB2, apb-aggregate, apb-fasta, apb-proteobench and MultiQC CLIs. Frontend tests run the TypeScript projections and controller behavior through tsx; Python route tests verify content-hashed assets are served correctly. Package smoke verifies both entry documents and their referenced bundles are present in the wheel.
